# Labelling guide

Guide version: 2

This guide says how to label the precision-study samples written by
`python evals/run_precision.py sample` and how to record known misses. Version 1 was never
written down: it was the rubric applied by hand to the 1.0.1 baseline and 1.0.2 labels
(`evals/labels/baseline/`, `evals/labels/after/`). Version 2 writes that rubric down unchanged
and adds the `fn` label. When a rule below changes in a way that would flip earlier labels, bump
the version and say what changed in the history at the end. `run_precision.py` records the version
in `_population.json` and prints it in the report, so you can tell which guide a set of labels
followed.

## The question behind every label

Picture the finding in the scanner's report for a team that runs this code as a deployed service.
Would a reviewer who knows the code want it on that list?

- **`tp`**: yes. The finding names a real problem of the kind the rule describes, at that place,
  and fixing it would make the service better. A real but minor problem is still `tp`; say so in
  the note ("low impact", "dev tooling").
- **`fp`**: no. The finding is wrong, or right in a narrow technical sense but not worth a user's
  attention in a deployed service: test fixtures, docs and examples, generated or vendored code,
  deliberate and commented choices, framework scaffolds, and code the rule misreads.
- **`unsure`**: you cannot decide from the repository alone, or the case sits on the boundary the
  rule was written around (for example a dev-only route that is only mounted in a local
  environment). `unsure` is left out of precision, so do not use it to avoid a hard call; use it
  when another careful reader could reasonably pick the other label.
- **`fn`**: a known miss. The rule should have reported something here and did not. These go in
  `evals/labels/fn/`, never in the sample sheets (see below).

An empty `label` means not yet labelled; the report counts those separately.

## How to label a sample entry

1. Open the file at the line in the entry. Read enough context to know what the code does: the
   whole function, the router setup, the config that wires it in, and where it is deployed. Auth,
   validation and limits are often set in another file; look for them before you say `tp`.
2. Decide using the question above and the rule notes below. Judge the finding, not the rule: if
   the rule fired for the wrong reason but the code really has that problem, it is still `tp`.
3. Write a one-line `note` with the reason, specific enough that someone else can check it
   without redoing the work: name the file, function or line that settles it. Good: "Auth via
   v1.Use(AuthMiddleware(true)) in hello.go". Bad: "has auth".
4. When the same code was labelled before (the baseline or an earlier version), keep the label
   unless the code or this guide changed, and say "(same as baseline)" or why it changed.
5. Never edit any other field. The sheet keys are `repo`, `file`, `line`, `snippet`,
   `fingerprint`, `label`, `note`.

## Cases that are always `fp`

- Test code, test fixtures and test data (`tests/`, `testdata/`, `*_test.go`, spec helpers),
  even when the rule's own test filter missed them.
- Documentation and examples: docstrings, OpenAPI or README examples, sample responses.
- Generated, vendored or third-party code (migrations generated by a framework, minified assets,
  vendored libraries), unless the team edits it by hand.
- Deliberate, visible choices: a commented best-effort `except: pass`, a dev-only Dockerfile that
  says so in its header, a public login or register route.
- Framework scaffolds left as the framework ships them (stock Laravel bootstrap, default service
  providers).
- Throwaway credentials used only by CI services or local Compose stacks.

## Cases that are usually `tp`

- The problem is in code that runs in production, nothing elsewhere in the repo handles it, and
  the fix is the one the rule suggests.
- A real problem with low impact (dev tooling without timeouts, a small unlocked asset build).
  Label `tp` and note the impact.

## Known misses (`fn`)

Recall needs misses, and nobody can list every miss. So recall is measured per (repo, rule) pair:
pick a repo and a rule, read the repo for every place the rule should fire, and record the ones
the scanner did not report. Record the review in `evals/labels/fn/<repo>.json`:

```json
{
  "repo": "example-voting-app",
  "guide_version": "2",
  "reviewed_rules": ["k8s-no-probes", "k8s-no-limits"],
  "missed": [
    {"rule": "k8s-no-probes", "file": "k8s-specifications/worker-deployment.yaml", "line": 18,
     "label": "fn", "note": "worker container has no probes; skipped because it declares no ports"}
  ]
}
```

- `reviewed_rules` lists every rule you reviewed the repo for, including rules where you found
  no miss. A rule reviewed with no misses gives that repo a recall of 100% for the rule; a rule
  not listed gives no recall at all (the report shows n/a, never 100%).
- Each `missed` entry has `rule`, `file`, `line`, `label` (always `fn`) and a `note`. A miss for a
  rule not in `reviewed_rules` is an error.
- Count a miss only when the finding would be `tp` under this guide. A case the rule skips by
  design (named in its `limitations` in `docs/rules.md`) is still a miss: recall measures what
  users get, and the limitations explain why.
- Files starting with `_` (such as `_template.json`) are ignored.

The report computes recall = tp / (tp + fn) using only the tp labels drawn from repos reviewed for
that rule, and F1 = 2PR / (P + R) with precision from all labels. Recall is an upper bound: it
counts only the misses someone found.

## Rule notes

What the rules look for is in `docs/rules.md`. These notes record the calls made so far, so the
next labeller makes the same ones.

### ci-no-test-step

`tp` when no workflow of that CI system runs the test suite and the repo has tests (or should).
`fp` when tests run in a script the rule did not recognise (read `./build.sh` and friends), or
for a repo with nothing to test (docs, config-only). A repo whose only workflow is a security
scan or deploy is `tp` if it has a test suite nobody runs in CI.

### console-logging-only

`tp` when a service reports errors or events through `console.log` / `print` / `fmt.Println`
and has no logger anywhere. `fp` for CLIs and scripts whose output is meant for a terminal.

### docker-latest-tag

`tp` for a production or CI image built from `:latest` or an untagged base. `fp` for local-only
images that say so, and for a `FROM` that is really another stage the rule did not link.

### docker-no-healthcheck

`tp` for a service image that exposes a port where no orchestrator health check is visible.
`fp` for build, job or test images, and where health checks are configured outside the repo
and the README says so.

### docker-root-user

`tp` for a production image whose final stage runs as root. `fp` for local dev-only Dockerfiles
(per their header or name), test-runner images (Playwright, CI tools), and images such as nginx
whose workers drop privileges and serve static files only.

### god-module

`tp` for one class or module doing several unrelated jobs (forms, permissions, views and
messaging together; a grab-bag of unrelated utilities). `fp` for large but cohesive modules: a
collection of same-kind classes (validators, lookups, widgets, template filters), one class
hierarchy, or a base class with high fan-in because everything subclasses it. `unsure` when the
file is very large and that size is the cost, but it has one concern.

### hardcoded-secret

`tp` only for a real-looking secret value committed where production reads it (a random
`SECRET_KEY` in shared base settings, a long JWT secret in the main properties file). `fp` for
i18n labels ("Password"), validation strings, setting or env var names, enum constants, URL
segments, docstring and OpenAPI examples, test keys under `testdata/`, and CI or Compose service
passwords that only exist inside throwaway containers.

### http-no-timeout

`tp` for an outbound HTTP call without a timeout on a request path (login flows, webhooks).
Dev tooling without a timeout is `tp` with "low impact" in the note.

### import-cycle

`tp` for a real module-level cycle that works only because of import order. `fp` when the back
edge is a function-local (deferred) import, or the chain runs through a package `__init__` that
re-exports submodules, or the import sits after the names it needs on purpose (registration
pattern). Two TypeScript models importing each other at module level is `tp` (commonly benign,
but real).

### k8s-no-limits

`tp` for a Deployment or StatefulSet container with no resource limits where no LimitRange,
Kustomize patch or Helm value in the repo sets them. `fp` for manifests that are clearly a local
demo (kind or minikube only, documented as such) and for limits set by a patch the rule did not
read.

### k8s-no-probes

`tp` for a serving container (it declares ports) with no readiness or liveness probe. `fp` for
datastores run only for a demo when the README says not to use them in production, and for
probes added by a patch or a mesh the repo configures.

### list-route-no-pagination

`tp` for a public list endpoint over a table that grows with use (products, users, orders).
`fp` for small fixed tables (countries, roles, plans) and for lists paginated by middleware or a
helper the rule did not read.

### missing-lockfile

`tp` for an app (not a library) whose installs are not reproducible because no lockfile is
committed; low severity, note it. `fp` for libraries, where a lockfile is optional.

### mixed-error-shapes

`tp` when clients of one service really receive incompatible error bodies. `fp` when the odd
response is unreachable, internal, or rewritten by a central error handler before it leaves the
service.

### no-health-endpoint

`tp` for a deployed HTTP service with no health or readiness route and no health-check library.
`fp` for libraries, CLIs and static sites. A Compose health check on the database only does not
count as the app's health endpoint.

### no-tests

`tp` for a folder of real logic (a package, service or resolver) with no tests anywhere in the
repo. `fp` when its tests live elsewhere (a root `tests/` tree, integration tests that exercise
it), and for folders with nothing worth unit testing: migrations, translations, templates and
views, framework wiring and service providers, vendored front-end assets, presentational UI
wrappers, a single trivial helper.

### no-version-prefix

`tp` for a public JSON API whose routes have no version segment and no other versioning. `fp`
for server-rendered sites, internal services and BFFs. A variable named `v1` is not versioning.

### openapi-drift

`tp` when the committed spec and the code really disagree (a route missing from the spec, a
spec path with no handler). `fp` when both describe the same route and the rule failed to join
them (a router mounted under a prefix it did not resolve, path parameters spelled differently).
Read the mount points before labelling each entry.

### query-in-loop

`tp` for an N+1: one query per row of data that grows with use, on a request path. `fp` for DDL
or schema-bounded loops (migrations, schema editors, integrity checks per foreign key), queued
DDL, and documented deliberate per-item work. `unsure` for an N+1 shape on a cold path such as
dev-time introspection.

### retry-no-backoff

`tp` for a retry loop around a network call that retries immediately. `fp` when backoff comes
from a helper or client library the rule did not see, and for loops that count login attempts.

### sql-string-concat

`tp` only when a value a caller can influence reaches the SQL string. `fp` when the interpolated
part is a constant identifier (quoted table or column name), a server-generated value, or a
placeholder list, and for one-time migrations with no user input.

### swallowed-error

`tp` for an error dropped with no log, comment or fallback where losing it hides a real failure
(a plugin that fails to load and vanishes). `fp` for commented best-effort code, expected
exceptions used as control flow (`try/except/else`, a fallback to a default), cleanup in
`finally`-like paths, and stock framework scaffolds.

### unauth-write-route

`tp` for a write route reachable without authentication that should require it. `fp` when auth
is applied elsewhere: router or group middleware (`v1.Use(AuthMiddleware)`), a controller
constructor (`$this->middleware('auth')`), a base controller (`before_action
:authenticate_user!`), CanCan `load_and_authorize_resource`, or a global security chain. Also `fp`
for public-by-design routes (login, register) and for resource routes whose controller never
defines that action. `unsure` for routes only mounted in a local environment.

### unbounded-query

`tp` for a query on a request path that reads every row of a table that grows. `fp` for SQL in
docstrings, introspection queries and bounded admin or maintenance code.

### unpinned-dependency

`tp` for an app whose deploys can pull a different version than the one tested. `fp` for
libraries (ranges are correct there) and for requirements files that a committed lockfile or
constraints file pins.

### unvalidated-body

`tp` when a handler uses the raw request body without checking its shape and a malformed body
can corrupt data or crash the handler. `fp` when validation happens in middleware, a model
layer (Mongoose schema validation counts) or a called function the rule did not read.
